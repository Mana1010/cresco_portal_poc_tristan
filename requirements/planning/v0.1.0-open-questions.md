## B. Data gaps (POC has no source data for these)

5. **Staff "Lens" field.** Per the design doc, Lens ∈ {None, Cost, Time, Quality, Scale}. In the POC's Org Chart image, only 2 of 27 staff show a Lens (Shannon Oke → Cost, Nick Munro → Time); nobody shows Quality or Scale. Import everyone else as Lens = None, per the visible data? **Answer:**

6. **Staff "Level" field.** The design doc's Staff field list is just Name/Position/Lens, but the POC displays a level badge (L1–L5) constantly (e.g. "Glenn Frewin (L3)") and the source data (`PO_STAFF[].level`) has it for every staff member. Should I add a Level field to Staff and import it, even though it wasn't in the written spec? **Answer:**

> Yes. Include a Level field and import the Level values from the HTML source.

7. **Project "Payment" field.** The Overview tab shows Payment as "✓ Paid" or "Outstanding", but the POC's underlying project data (`MP` array) has no field driving that value for the Project Detail view — the render reads `p.pd`, which isn't populated anywhere in the 50 seeded projects (a different `pd` is used elsewhere for proposals). Should I: (a) treat every imported project as "Outstanding" since that's what the POC would actually render today, (b) pick a different derivation (e.g. tie it to Status codes like "11 Released — Awaiting Payment"), or (c) leave Payment out of scope for this version? **Answer:**

> Keep Payment as a random/placeholder value for v0.1.0. In a future version, this will be transformed into a summary field based on values from a linked Payment doctype.

## C. Field/schema decisions

8. **Project Type values.** The list view shows short codes (`STR-RESI`), the Overview tab shows full labels ("Structural — Residential"). Should Type be a Select field storing the code (with the label just used for display), or should I create a small "Project Type" master doctype holding code + label pairs? **Answer:**

> Use a Select field storing the short Project Type code (e.g. `STR-RESI`). The corresponding long labels should be handled through a small fixed lookup in code rather than a separate Project Type doctype.

9. **Tier: stored vs. computed.** The POC computes Tier live from two things — a Tier×Volume complexity score and a Fee-based tier — then takes the more severe of the two. Should v0.1.0 just import the already-resolved Tier value per project (simplest, matches "field types from the data" instruction), or should I reproduce the calculation as logic (e.g. a server script) so Tier recalculates if Fee/Complexity change later? **Answer:**

> Tier should be a computed field. Use the Tier Input and Volume Input to calculate the Complexity Score and resulting Tier. During testing, verify that the resulting Tier values match what appears in the HTML file.

10. **Document Register "Status" values.** POC renders this as a checkmark or "Pending" (binary). Is `Select: Submitted, Pending` fine, or would you prefer a Check(box)/boolean field instead? **Answer:**

> Use the binary status represented by the POC: `Submitted` and `Pending`. A Select field is acceptable.

11. **Document Register "Document" values.** Each Project Type has a fixed 4–7 item document checklist in the POC (e.g. STR-RESI → Site Survey, Architectural Plans, Geotech Report, Council Approvals, Existing Structural Dwgs). Import these as free-text Data rows (seeded from the template at import time), or do you want a master list of Document Types validated against Project Type? **Answer:**

> Generate/populate the Document Register rows from the existing POC document templates based on the Project Type and Doc Path. A separate Document Type master doctype is not required for v0.1.0.

12. **Project Deliverable — QA chain.** Each deliverable in the POC carries its own 5-step QA reviewer chain (L1 Peer → L5 Director, varies by Tier) shown as "1/5" with a "View →" link. Since QA Chain isn't one of the 7 doctypes for this version, should Project Deliverable just have Deliverable/Fee/Status (no QA sub-tracking), confirming that's intentionally deferred? **Answer:**

> Include a QA field in the Project Deliverable child doctype, but leave it empty/unused until the QA Chain is implemented in a later version.

13. **Project Transmittal — is it built with no UI this version?** It's listed as a doctype to build (with data imported), but the "Transmittals" tab isn't in this version's Portal Pages scope. Confirm: import the transmittal data into the doctype, but no portal UI for it yet (it'll just live on the Project record, viewable via the Frappe desk)? **Answer:**

> Yes. Create/import the Transmittal child records as part of the backend data, but the Transmittals portal tab/UI is out of scope for v0.1.0.

## D. Portal page behavior

14. **Non-scoped sidebar sections.** The POC's left nav has many sections (Dashboard, AI Layer, Inspections, Programme, Operations, Client) that aren't part of this version. Should the portal for v0.1.0: (a) show only Projects and Risk Register in the nav, (b) show the full POC nav with the other links disabled/greyed out for visual fidelity, or (c) something else? **Answer:**

> Non-scoped sections should not be functional in v0.1.0. If they are shown for visual fidelity, they should be disabled/placeholder links. Only functionality backed by this version should be accessible.

15. **Top bar stats & chrome.** The header shows "173 KPIs · 50 Projects · 20 Roles · 3 live AI alerts · 2 inspections booked", an "AI ON" toggle, and login info. None of these (besides Projects count) have backing data this version. OK to compute Projects count live and hardcode/hide the rest, or do you want them removed entirely from the header for this version? **Answer:**

> Only values backed by v0.1.0 data should be functional. The Projects count can be computed from the Project records. Other statistics such as KPIs, Roles, AI alerts, and inspections should be treated as placeholders or hidden because their underlying features are out of scope.

16. **Non-scoped Project Detail tabs.** Overview and Documents are the only tabs being built. Should the tab strip still show Labs/QA Chain/Transmittals/Variations as disabled tabs (matching the POC look), or should the tab strip only show Overview/Documents? **Answer:**

> Only Overview and Documents should be implemented in v0.1.0. Labs, QA Chain, Transmittals, and Variations are out of scope and should not be built.

17. **Data visibility / access control.** Should every logged-in portal user see all 50 projects and all risk register rows (matching the POC, which shows the same data regardless of "logged in" user), or do you want filtering by Owner/Lead per logged-in Staff for this version already? **Answer:**

18. **Portal user accounts.** Do you want Staff records linked to real Frappe User logins for this POC (so specific people can log in), or is a single shared/test login sufficient to demo the 3 pages? **Answer:**

> Staff records should link to real Frappe User accounts. The portal is intended for authenticated internal staff users. A future portal-facing registration/login flow may support different staff/client access levels, but the registration UI itself is not part of v0.1.0.
