# Cresco Portal Core POC — v0.1.0 Implementation Plan (Draft for Review)

This plan is derived from `requirements/Version 0.1.0 - Cresco Portal Core POC Design.md`, the marked-up
screenshots in `requirements/`, and the embedded data/logic inside
`requirements/Cresco_Platform_POC_V3_1_11.html`. It has **not** started execution — see
[v0.1.0-open-questions.md](v0.1.0-open-questions.md) for the decisions needed before/while building.

## 1. Scope for this version

**In scope:**
- 7 doctypes: Project, Project Deliverable (child), Project Document Register (child), Project Transmittal
  (child), Client, Staff, Risk Register.
- One-time import of the data already embedded in the POC HTML into those doctypes.
- 3 portal pages (Frappe website/portal, Vue 3 + Tailwind): **Projects** (list), **Project Detail**
  (Overview tab + Documents tab only), **Risk Register** (list).

**Explicitly out of scope for v0.1.0** (present in the POC HTML but not mentioned in the Portal Pages
section of the design doc): Dashboard, Dashboard Tiers, New Proposal, Approvals, KPI Analytics,
Anti-Gaming Pairs, the entire AI Layer (Inbox/Alerts/Manifest/Governance/Audit), Inspections (Part A/B),
Programme (Phases & Envelope, Org Chart), Operations (Process Flow, Scorecards, Staff Workflow, Issue
Register, Write-Offs, Time Recording, Governance), Client View portal, and the Project Detail sub-tabs
**Labs, QA Chain, Transmittals, Variations** (Transmittal *data* is still imported into the doctype per
the DocTypes section — it's only the UI tab that's deferred).

## 3. Data import approach

1. Write a one-off Node/Python extraction script that pulls the relevant JS object literals
   (`MP`, `PO_STAFF`, `RISKS_V13`, `PTYPES`, `ST`, `DOCS`) out of the POC HTML and converts them to JSON.
2. Transform that JSON into Frappe fixtures (`.json`) or CSV suitable for the Data Import tool, resolving
   the string-based references (`cl`, `po`, `le`) into Client/Staff doctype links, and expanding each
   project's Document Register rows from the `DOCS[type]` template + `dp` (doc path) plus seeding
   Deliverable rows from the existing POC seed logic (`seedExistingDeliverables`) minus the QA sub-chain.
3. Run the import via a Frappe `patch`/`bench execute` script (kept in the app under
   `patches`/`fixtures`) rather than a manual UI import, so it's re-runnable and version-controlled.
4. Validate row counts after import: 50 Projects, 25 Clients, 27 Staff, 14 Risk Register entries, and
   Deliverable/Document Register/Transmittal children matching the POC's per-project data.

## 4. Portal pages architecture

- Follow the [Frappe Portal Pages guide](https://docs.frappe.io/framework/user/en/portal-pages): pages
  live under `www/` in the app, each with a `.py` (context/auth) + `.html` (mount point) pair, with Vue 3
  mounted into that page and Tailwind for styling.
- **Projects** (`/projects`): server-side `get_context` fetches the Project list (or exposes a whitelisted
  API the Vue app calls); client-side filter box narrows the already-fetched rows; row click routes to
  `/projects/<id>`.
- **Project Detail** (`/projects/<id>`): Overview tab (Details panel + Deliverables table) and Documents
  tab (Document Register table) only; other tabs from the POC are not built this version, but the tab
  strip can still render their (disabled/greyed) labels for visual fidelity ⚠ confirm.
- **Risk Register** (`/risk-register`): read-only table, no create/edit in this version.
- Reuse the POC's exact color tokens (`B`, `T`, `SC2` from the HTML) as a small shared Tailwind
  config/CSS-variables file so the UI matches pixel-for-pixel.
- Left nav / top bar: render only the entries actually backed by something in this version (Projects,
  Risk Register); either hide the rest of the POC's sidebar sections or render them as visually-present
  but disabled links ⚠ confirm. Top bar counters (`173 KPIs`, `20 Roles`, etc.) have no backing doctype
  this version — plan is to compute what we can (Projects count) and hardcode or hide the rest ⚠ confirm.

## 5. Access / auth

- Portal pages require a logged-in Frappe **Website User**; no public/anonymous access.
- v0.1.0 shows the same project/risk data to every logged-in user (no per-owner filtering), matching the
  POC's behavior of always showing all 50 projects regardless of which staff member is "logged in" ⚠ confirm.
- Mapping an actual login (`tristan@servio.ph`, etc.) to a Staff record, and the "AI ON" toggle /
  login-info chip in the header, are cosmetic only this version (no functional AI layer).

## 6. Environment & repo setup — DONE

- Target repo: `https://github.com/Mana1010/cresco_portal_poc_tristan` (`origin`). Per decision, committing
  straight to `main` (no feature branch/PR for this version).
- Dev environment: WSL2 Ubuntu 24.04 (`wsl -d Ubuntu`), bench installed directly (via pipx,
  `frappe-bench` 5.31.0), reusing the existing `~/frappe-bench-16` bench (Frappe v16.25.0, MariaDB
  10.11, Redis 7.0 already running as systemd services there) rather than provisioning a new bench from
  scratch.
- **Important discovery, resolved with the user:** that bench already had a *different*, much more
  advanced `cresco_portal` app + `cresco-test.local` site installed (tracking
  `github.com/CrescoAU/cresco_portal`, branch `staging` — an unrelated, ongoing "Project-First"
  implementation with its own roadmap/handoff docs). Decision: leave that app/site completely untouched
  and build this POC as a **new, separate app and site** in the same bench:
  - App: `cresco_portal_poc` (created via `bench new-app`)
  - Site: `cresco-portal-poc.local` (created via `bench new-site`, admin password `admin` for local dev)
  - `cresco_portal_poc` installed on that site (`bench --site cresco-portal-poc.local install-app cresco_portal_poc`)
- The `cresco_portal_poc` app folder itself (`~/frappe-bench-16/apps/cresco_portal_poc`) is the git repo
  that maps to `cresco_portal_poc_tristan` on GitHub — `origin` was added there, and its
  `feat: Initialize App` commit was merged with the pre-existing `requirements/` history
  (`--allow-unrelated-histories`) so both the app source and the design docs live in one repo, branch
  `main`.
- Gotchas hit and resolved along the way (for anyone else setting this bench up):
  - `bench` isn't on `PATH` by default here — it's a pipx install at `~/.local/bin/bench`, and node comes
    from `nvm` (`v24.18.0`), not the `/mnt/c/...` Windows node picked up by default `$PATH`. Every bench
    command needs `source ~/.nvm/nvm.sh && nvm use 24` and `~/.local/bin` prioritized on `PATH` first.
  - `sudo` needs an interactive password this agent doesn't have, but `wsl.exe -u root` runs commands as
    root directly, sidestepping that.
  - MariaDB root password was supplied by the user directly (not reset/touched) to avoid restarting the
    DB service the existing `cresco-test.local` site depends on.

## 7. Data-modeling details worked out from the POC (per user's answers)

- **Staff hierarchy / Lens inheritance (Q5).** The POC's Org Chart tab has a full `ORG` tree (not just the
  27-entry `PO_STAFF` list) with real reporting lines and 4 top-level Lens assignments by role:
  Business Manager → Cost, Operations Manager → Time, Engineering Manager → Quality, G&I Manager → Scale.
  Plan: add a **Reports To** (Link → Staff) field to Staff, import the full `ORG` tree (31 named people —
  4 more than `PO_STAFF`: Madi Platt, Regine Estrella, Paul Dyason, Cathleen Rodriguez, all coordinators
  under Shannon Oke), and compute **Lens** in a `validate`/`before_save` hook by walking the Reports To
  chain up to the nearest ancestor with an explicit Lens (or None if none found, e.g. the Director).
  `EA (TBH)` and `Vacant` are unfilled placeholder positions in the POC, not real staff — excluded from
  import.
- **Level field (Q6).** Imported directly from `PO_STAFF[].level` / the `ORG` tree's `level`.
- **Payment field (Q7).** Random/placeholder per project for v0.1.0 (no derivation logic); flagged in
  code as a placeholder pending a future Payment doctype.
- **Type field (Q8).** Select field storing the short code (`STR-RESI`, etc.); the long label
  ("Structural — Residential") lives in a small fixed code→label lookup in the app code (mirrors the
  POC's own `PTYPES` table), not a separate doctype.
- **Tier (Q9).** Computed, reproducing the POC's actual logic so results match the HTML exactly: Tier
  Factor (T) × Volume Factor (V) → a T×V-based tier (`≤2 Green, ≤6 Blue, ≤9 Amber, else Red`), separately
  a Fee-based tier (`>50000 Red, >20000 Amber, >5000 Blue, else Green`), final Tier = the more severe of
  the two. Implemented in Project's controller so it recalculates if Fee/T/V change later, and validated
  against all 50 imported projects' actual POC tier values.
- **Document Register (Q10, Q11).** Status is a 2-option Select (`Submitted`, `Pending`). Rows are
  generated per project from the POC's fixed `DOCS[project type]` checklist, with the submitted/pending
  split driven by `Doc Path`: Doc Path 1 → all rows Submitted; Doc Path 2–4 → all but the last 2 rows
  Submitted, last 2 Pending (reproducing the POC's exact `sub = i < docs.length - (dp===1 ? 0 : 2)` rule).
- **Project Deliverable QA field (Q12).** A QA field is added to the child doctype but left empty/unused
  in v0.1.0 (no QA Chain doctype/logic this version). Deliverable rows themselves (name, fee, status) are
  generated from the POC's `DEL_TEMPLATES[project type]` list, fee-scaled proportionally to the project's
  total Fee, matching `seedExistingDeliverables()`.
- **Transmittal (Q13).** Imported as data only; no portal UI this version.

## 7. Proposed build sequence

1. Dev environment stood up (bench/site/app scaffold) — blocked on Q in open-questions doc.
2. Doctypes created (Client, Staff, Project + 3 child tables, Risk Register) with fields above.
3. Data-extraction + import script written and run against the 7 doctypes; row counts verified.
4. Portal page shell (layout, nav, Tailwind theme matching POC colors) for the 3 pages.
5. Projects list page wired to real data (filter, sort, row click).
6. Project Detail page — Overview tab, then Documents tab.
7. Risk Register page wired to real data.
8. Pass over visual fidelity vs. the POC screenshots; fix gaps.
9. Push branch, open PR.

## 8. Portal/process decisions confirmed by the user

- Non-scoped sidebar sections (Dashboard, AI Layer, Inspections, Programme, Operations, Client) are not
  functional in v0.1.0; if shown for visual fidelity they're disabled/placeholder links (Q14).
- Top bar: Projects count is computed live from real data; other stats (KPIs, Roles, AI alerts,
  inspections) are placeholders or hidden (Q15).
- Project Detail tab strip only implements Overview and Documents — Labs/QA Chain/Transmittals/Variations
  are not built at all this version, not even as disabled tabs (Q16).
- No per-user data filtering: every authenticated staff user sees all 50 projects and the full Risk
  Register (Q17).
- Staff records link to real Frappe User accounts; portal is for authenticated internal staff (Q18).
- Commit straight to `main`, no feature branch/PR (Q19).
- Review checkpoints: after data migration, and during UI implementation as appropriate, in addition to
  this pre-execution review (Q20).
